# Family flow reconciliation (report only)

This command produces an evidence report from a PostgreSQL database. It has no apply mode and does not repair rows, create balances, change subscription state, or initiate payments. Run it only against an explicitly selected environment after its latest schema migrations have completed.

The database connection is read only from the `MEALMATE_DB_CONNECTION` environment variable. The caller must also name the environment explicitly:

```powershell
$env:MEALMATE_DB_CONNECTION = '<operator-supplied PostgreSQL connection>'
dotnet run --project tools/FamilyFlowReconciliation/FamilyFlowReconciliation.csproj -- --environment staging
```

Use a secret manager or protected operator shell to provide the connection value. Do not paste it into command history, tickets, reports, or application settings. The report prints the environment label, generation time, Kuwait business date, aggregate counters, stable record identifiers, evidence codes, and a deterministic fingerprint; it omits customer names and connection details. The `Findings` list is capped at 200 rows per code and the aggregate counters cover the full selected environment.

The command opens one PostgreSQL `REPEATABLE READ` transaction, sets `TRANSACTION READ ONLY` before issuing report queries, verifies `SHOW transaction_read_only` returns `on`, and uses EF `AsNoTracking`. A failed read-only check aborts the report. The fingerprint covers stable report content and business date; the generation timestamp is intentionally excluded.

Review findings with the source payment attempt, verified receipt, saved batch allocation, actual service-day rows, persisted dispatch/print evidence, frozen address snapshot, cancellation settlement and refund calculation. `selected_member_account_missing` describes a selected checkout line without a linked customer account; a deferred member is not a payment failure. `paid_batch_unknown_payer_or_net`, `paid_batch_needs_review` and `family_paid_subscription_missing_immutable_batch_evidence` identify missing or contradictory immutable payment/allocation evidence; they do not authorize a guessed amount. `paid_preparing_calendar_not_materialized` marks a future-dated `Paid`/`Scheduled` subscription with no day rows as informational only when the saved batch, payer, paid attempt, verified receipt, conserved allocation and not-yet-fulfilled state agree. A payment timestamp or status alone does not establish payment. `paid_ready_member_without_service_days` marks current/active cases, completed-without-days contradictions, or future subscriptions without coherent batch proof for review. The aggregate `PaidReadyWithoutDays` counter is an observation count across both categories. Neither finding proves delivery. Profile-versus-purchase address differences are expected when the batch retained the original purchase snapshot; incomplete frozen lineage is reported separately. A future `Open` day with only a confirmation timestamp is not treated as confirmed or dispatched when supporting evidence is absent. A report finding never authorizes a wallet credit, refund, or data repair.

CI builds this standalone project explicitly and runs its nonempty disposable-PostgreSQL regression. The integration test migrates a Testcontainers database, runs the report twice, checks stable fingerprint/business date and nonzero expected finding counters, verifies both the informational future-preparing and current-service-review cases, confirms the actual transaction is read only, and compares before/after counts and row-content hashes for family, payment, service, cancellation, wallet, address and amendment tables. It also verifies PostgreSQL rejects a direct write inside a read-only transaction. These checks are not a production rehearsal or an operator approval.

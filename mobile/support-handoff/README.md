# حزمة تنفيذ الدعم لتطبيقات الجوال

هذه الحزمة توضح عقد الواجهة وسلوك المنتج المطلوب لفريقي تطبيق العميل وتطبيق السائق ومسؤول التوصيل. لا يحتوي هذا المستودع على مشروع تطبيق جوال معتمد أو معرفات حزم/توقيع/بناء؛ لذلك هذه مواصفات تسليم للتنفيذ وليست إثباتاً على اكتمال تطبيق أو اختباره.

## قواعد مشتركة

1. أرسل Bearer session المعتادة. الخادم هو مصدر الحقيقة لنوع المستخدم، المستخدم، المطعم، الصلاحيات، والعضوية المحفوظة. لا تعتبر `userId` أو `restaurantId` من العميل تفويضاً.
2. خزّن كل التواريخ وأرسلها بصيغة UTC مع لاحقة `Z`. اعرض التوقيت المحلي للقراءة فقط.
3. نطاق عرض الحالة يقرره الخادم في كل قراءة وكتابة. طالب الحالة يرى محادثته العامة؛ مستلم المهمة يرى نص المهمة ومحادثتها فقط؛ الملاحظات الداخلية لا تظهر للأطراف. إلغاء المهمة يسحب الوصول. لا تنسخ حقولاً محجوبة إلى ذاكرة التطبيق أو الإشعارات.
4. عند `409 support.version_conflict` أعد جلب الحالة، اعرض للمستخدم مسودته والتغييرات الحالية، واطلب منه تأكيد الإرسال مجدداً بمفتاح جديد وإصدار الخادم الحالي. لا تعِد تشكيل الرسالة بصمت.
5. للطلبات التي يثبت العقد أنها idempotent فقط: احتفظ بالـ payload والـ `idempotencyKey` نفسيهما بعد timeout أو انقطاع أو `5xx` وأعد الطلب مطابقاً تماماً. لا تستخدم مفتاحاً واحداً لعمليتين ولا تغيّر payload أثناء إعادة المحاولة. لا تنفذ إعادة تشغيل تلقائية في الخلفية.
6. اكتب المسودات المحلية تحت نطاق `API base URL + actor user id + role`; امسح المسودات والمفاتيح والملفات المؤقتة عند logout أو تبديل الحساب/البيئة. لا تضع Bearer token في سجل أو رابط.
7. عند رفع مرفق، لا تكرر رفع الملف تلقائياً إذا ضاع الرد؛ الرفع لا يملك مفتاح idempotency عاماً. احتفظ بالمفتاح الذي استلمته إن عُرف، وصالح حالة الرفع قبل إعادة المحاولة. إن لم تعرف نتيجة الرفع، أخبر المستخدم بأن إعادة الرفع قد تنشئ ملفاً غير مربوط. عامل تنظيف مرفقات الدعم يعمل دورياً بعد مهلة 24 ساعة، ويحمي أي ملف مرتبط برسالة؛ لا تفترض أن حذفاً فورياً حدث بعد الرفض.
8. اقرأ المرفقات فقط من `readPath` المعاد ضمن رسالة مرئية وبطلب موثق. لا تستخدم URL عام أو مفتاح التخزين في واجهة العرض. رفض الفحص أو تعذر `clamd` يعني أن الدليل لا يقرأ؛ اعرض حالة قابلة لإعادة المحاولة بعد استعادة الخدمة.
9. استخدم نصاً عاماً آمناً في إشعارات الجهاز. أرسل معرف الحالة/المسار فقط؛ عند فتح رابط بارد أو دافئ أو بعد reconnect أعد جلب الحالة من API وتعامل مع `401/403/404` كإلغاء وصول.
10. لا تعتبر حالة دعم دليلاً على رد مال أو تعويض مالي. لا تنفذ أي أثر مالي من شاشة الدعم.

## خريطة المسارات الموجودة

| الغرض | المسار الفعلي | ملاحظات |
|---|---|---|
| قائمة الحالات المقروءة للمستخدم | `GET /api/v1/support/cases` | ترقيم `pageNumber/pageSize`; النتائج مقيدة بعضوية ودور المستدعي. |
| فتح حالة عامة | `POST /api/v1/support/cases` | `CreateSupportCaseRequest`; `IdempotencyKey` إلزامي. الخادم يحدد الفريق. |
| تفاصيل الحالة | `GET /api/v1/support/cases/{caseId}` | يرجع الرسائل والمهام المرئية فقط. |
| إرسال رسالة عامة/رد مهمة | `POST /api/v1/support/cases/{caseId}/messages` | `body, expectedVersion, idempotencyKey`; أرسل `taskId` فقط لمهمة مصرح بها. |
| إجراء حالة/مهمة | `POST /api/v1/support/cases/{caseId}/actions/{operation}` | أمثلة: `reopen`, `close`, `complete-party-task`; راجع العقد المشترك للقيود. |
| رفع دليل الحالة | `POST /api/v1/support/attachments` | multipart بحقل `file`; لا idempotency عام. |
| قراءة مرفق رسالة | `GET /api/v1/support/cases/{caseId}/messages/{messageId}/attachments/{index}` | Bearer والتحقق من صلاحية الحالة/الرسالة في كل طلب. |
| صندوق إشعارات العميل | `GET /api/v1/customers/me/notifications`, `PUT /api/v1/customers/me/notifications/{id}/read`, `PUT /api/v1/customers/me/notifications/read-all` | Inbox وطلب push لحالات الدعم العامة يُحفظان معاً؛ تسليم المصدر at-least-once ويحتاج Firebase staging/client verification. تسجيل/إلغاء جهاز العميل عبر `PUT/DELETE /api/v1/customers/me/device-tokens`. |
| صندوق السائق وتسجيل جهازه | `GET /api/v1/driver/notifications`, `PUT /api/v1/driver/notifications/{id}/read`, `POST/DELETE /api/v1/driver/device-token` | Inbox وطلب push لحالات الدعم العامة يُحفظان معاً؛ إعادة التحقق من الحساب والملف وtoken عند الإرسال. المصدر لا يثبت Firebase staging/client verification. |
| صندوق مسؤول التوصيل وجهازه | `GET /api/v1/delivery-manager/notifications`, `PUT /api/v1/delivery-manager/notifications/{id}/read`, `POST/DELETE /api/v1/delivery-manager/device-token` | إشعارات الحالات/المهام لمسؤول التوصيل تستخدم outbox وFCM. |

مسارات `api/v1/support/cases` تخضع لـ `[Authorize]` وتفويض نطاقي داخل الخدمة. تطبيق الجوال يعرض فقط مواعيد الدورة التي يعيدها الخادم ولا ينشر السياسة. إدارة السياسة متاحة في لوحة الإدارة عند `/admin/support/timing`؛ القراءة تتطلب دور Admin محفوظاً ونشطاً من `SuperAdmin` أو `SupportView`، والنشر يتطلب `SuperAdmin` محفوظاً ونشطاً. المسارات هي `GET /api/v1/support/timing-policies`, و`GET /api/v1/support/timing-policies/active`, و`POST /api/v1/support/timing-policies/publish`. حالة إعداد السياسة في staging والإنتاج وقبول تطبيق الجوال غير متحققة هنا.

## تسليم وتشغيل

- كل تطبيق يطبق ملف دوره، ويستخدم مسارات البيئة التي يوفرها مالك البيئة. لا تضع مضيفاً أو مفتاحاً أو secret في هذه المواصفات.
- الدمج على المستودع/الفرع الأصلي للتطبيق، إعدادات Firebase/المتجر، التوقيع، والبناء مسؤولية فريق التطبيق؛ بياناتها غير متاحة هنا.
- لا تعتمد جاهزية الدور حتى تمر حالات القبول في ملفه على خادم staging ذي migrations و`clamd` متاحين، مع إثبات تسجيل الدخول والنطاق لكل دور.
- راجع خطة الملكية قبل إعلان إطلاق موحد: ما هو نقص كود، وما هو تحقق staging، وما هو تسليم خارجي موضح على حدة.

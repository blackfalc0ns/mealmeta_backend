# تسليم تعديلات تسجيل واعتماد السائقين إلى مبرمج الموبايل — MealMate

**تاريخ المراجعة:** 30 سبتمبر 2026  
**الجمهور:** مبرمج تطبيق السائقين ومختبر التكامل  
**النطاق:** التسجيل، الدخول قبل الاعتماد، رفع المستندات، متابعة الطلب، طلب التعديلات، إعادة التقديم، الموافقة والرفض، FCM ومركز الإشعارات. يشمل ملخص التغييرات في المطعم والأدمن التي تؤثر على تجربة السائق.  
**مصدر المعلومات:** الكود المحلي الحالي في المشروع بعد تعديلات Gemini والإصلاحات اللاحقة. هذا مستند تسليم لحالة الكود، وليس إعلانًا بأن النسخة منشورة على السيرفر أو أن كل الفجوات أُغلقت.

> اقرأ قسم «الفجوات المعروفة» قبل التنفيذ. توجد اختلافات فعلية بين بعض الاستجابات والأوامر، ولا يجب بناء التطبيق على افتراض أن هذه الاختلافات قد أُصلحت.

## 1. المطلوب من مبرمج الموبايل

1. توحيد شاشة متابعة الطلب على API الحالة، مع فصل موافقة المطعم عن الاعتماد النهائي.
2. دعم دخول السائق أثناء المراجعة، ثم تسجيل FCM باستخدام جلسة مصادقة فعلية.
3. استخدام رفع ملفات حقيقي وحفظ `storageKey` العائد من السيرفر.
4. تنفيذ تعديل الطلب وإعادة التقديم ببيانات الحقول المعدلة فقط، ومعالجة أخطاء الحالات النهائية والتغييرات الفارغة.
5. منع تغيير الهاتف في شاشة إعادة التقديم حاليًا.
6. التعامل مع إشعارات التسجيل كسبب لتحديث الحالة من السيرفر، مع دعم فتح الشاشة بعد تسجيل الدخول.
7. فصل هوية المستخدم وطلب التسجيل وملف السائق؛ هذه معرّفات مختلفة.
8. التعامل مع النصوص المترجمة والحقول الاختيارية دون افتراض أن الاستجابة تحتوي دائمًا على اللغتين.
9. تنفيذ سيناريوهات القبول الموجودة في نهاية الملف على بيئة التكامل.

## 2. ملخص التعديلات وتأثيرها على التطبيق

| التعديل في النظام | الأثر على الموبايل |
|---|---|
| ربط متابعة الطلب وإعادة التقديم بصاحب الطلب المسجل | إرسال Bearer token؛ رقم الهاتف أو `registrationId` وحده لا يعطي صلاحية |
| دعم إشعارات السائق بواسطة `UserId` قبل وجود `DriverProfileId` | لا تنتظر الاعتماد النهائي لتسجيل FCM أو تحميل مركز الإشعارات |
| إزالة الإرسال المباشر من أوامر التسجيل وإعادة التقديم التي أصبحت تستخدم Outbox | نجاح الطلب لا يعني وصول push فورًا؛ حدّث الشاشة من الاستجابة/API الحالة |
| تصحيح مقارنة الهوية ورقم الرخصة واللوحة بالقيم القديمة عند إعادة التقديم | تعديل هذه البيانات يعيد مراجعة المطعم، بدل إبقاء موافقته على بيانات قديمة |
| رفع مستند بديل يعيد مراجعة المطعم في مسار إعادة التقديم المرتبط بمطعم | أظهر مرحلة المراجعة الجديدة بعد تحميل الحالة؛ لا تعرض موافقة المطعم القديمة من cache |
| رفض تغيير الهاتف قبل تعديل البيانات | الهاتف للعرض فقط في إعادة التقديم، حتى يتوفر مسار تحقق مستقل |
| التحقق من وجود الملف ومحتواه في التسجيل الذاتي وإعادة التقديم والتسجيل من المطعم والاعتماد النهائي | مفاتيح وهمية أو ملفات فارغة تسبب فشل الطلب؛ لا تستخدم رابط المعاينة بدل المفتاح |
| منع إعادة فتح الطلب المعتمد أو المرفوض عبر resubmit | إخفاء زر إعادة التقديم في هاتين الحالتين ومعالجة `409` |
| منع إعادة تقديم طلب دون تغيير | لا تفعّل الإرسال ما لم يتغير حقل أو يُرفع مستند |
| السائق الذي ينشئه المطعم يبقى بانتظار اعتماد المنصة | إنشاء المطعم للحساب لا يفتح عمليات التوصيل |
| تحسين حالات المستندات والجاهزية في لوحة المطعم | انتهاء المستند يتغلب على شارة الموافقة القديمة؛ الموافقة ليست نفس حالة التوفر للعمل |
| إضافة تاريخ المراجعات للأدمن وتصفح إشعارات الأدمن والمطعم | هذه تغييرات لوحات؛ لا تنقل عقود pagination الخاصة بها إلى إشعارات السائق |

## 3. المعرّفات والحالات: لا تخلط بينها

| الاسم | المعنى | مصدره |
|---|---|---|
| `userId` | حساب Identity صاحب جلسة الدخول | استجابة الدخول/first-time-setup |
| `registrationId` | طلب تسجيل السائق ومراجعاته | استجابة التسجيل الذاتي، واستجابة الحالة |
| `id` في تفاصيل التسجيل | نفس معرّف طلب التسجيل، لكن باسم مختلف في DTO التفاصيل | `GET /api/v1/drivers/registrations/{id}` |
| `driverProfileId` | الملف التشغيلي للسائق | ملف السائق بعد إنشائه |
| `resultingDriverProfileId` | رابط الطلب إلى الملف الناتج إن وُجد | تفاصيل التسجيل؛ nullable |
| `restaurantId` | المطعم المختار؛ عدم وجوده يعني مسار مستقل | طلب التسجيل/الحالة |
| `notificationId` | إشعار محفوظ في مركز إشعارات السائق | قائمة الإشعارات |
| `subjectId` | الكيان الذي يشير إليه الإشعار؛ يكون طلب التسجيل لإشعارات التسجيل | قائمة الإشعارات |

**قبل الاعتماد قد توجد جلسة مستخدم وطلب تسجيل دون ملف سائق تشغيلي.** غياب `driverProfileId` لا يعني أن جلسة الدخول غير صالحة.

### 3.1 حالة الطلب `VerificationStatus`

القيم الحالية: `Draft=1`، `Submitted=2`، `UnderReview=3`، `Approved=4`، `Rejected=5`، `Expired=6`، `ResubmissionRequired=7`، `NeedsChanges=8`.

الإعداد الحالي للـJSON يرسل enums كأسماء نصية مثل `Approved`. يمكن دعم القيم الرقمية القديمة للتوافق، لكن لا تعتمد على ترجمة الشارة لمقارنة الحالة.

### 3.2 حالة الحساب `AccountStatus`

القيم الحالية: `Registered=1`، `PhonePending=2`، `Active=3`، `Suspended=4`، `Closed=5`.

`PendingApproval` و`PendingAdmin` ليستا قيمتين في enum حالة حساب Identity الحالي. قد تُستخدم تسميات انتظار مشابهة في حالة ملف/واجهة أخرى؛ لا تضعها في parser الخاص بـ`accountStatus`.

التسجيل الذاتي ينشئ الحساب بحالة `Registered`. تسجيل الدخول بكلمة المرور يسمح بهذه الحالة، لكنه يرفض `PhonePending` و`Suspended` و`Closed`. نجاح الدخول لا يساوي السماح بالعمل.

### 3.3 حالات المراجعتين

اقرأ الحقول الثلاثة مستقلة:

- `status`: حالة الطلب ككل.
- `restaurantApprovalStatus`: نتيجة مراجعة المطعم.
- `adminApprovalStatus`: نتيجة مراجعة إدارة المنصة.

السائق المستقل يُعفى من مراجعة المطعم في المسار الحالي، ويمكن أن يرجع `restaurantApprovalStatus=Approved` دون قرار من مطعم. تحديد المسار المستقل يكون بمعرّف المطعم، وليس بهذه القيمة وحدها.

## 4. الفلو من التسجيل إلى الاعتماد

### 4.1 تسجيل ذاتي مرتبط بمطعم

1. اختيار مطعم من API الخيارات، وإدخال الهوية والرخصة والمركبة.
2. رفع الملفات والحصول على مفاتيحها.
3. إرسال التسجيل الذاتي الكامل.
4. حفظ `registrationId`؛ استجابة التسجيل لا تحتوي على access/refresh tokens.
5. الدخول بكلمة المرور التي اختارها السائق أثناء التسجيل.
6. تسجيل FCM ثم جلب حالة الطلب.
7. الحالة الأولية الحالية: الطلب `Submitted`، ومراجعة المطعم `Submitted`، ومراجعة الأدمن `Submitted`.
8. موافقة المطعم تنقل الطلب إلى التدقيق النهائي؛ التطبيق يستمر في عرض شاشة المراجعة.
9. طلب تعديل يفتح نموذج التعديل ويعرض الملاحظات والجهة الطالبة.
10. الاعتماد النهائي يفتح تجربة السائق المعتمد بعد تحديث الحالة والملف التشغيلي والتحقق من حالة الحساب.

### 4.2 تسجيل ذاتي مستقل

أرسل `restaurantId=null`. لا ترسل معرّف مطعم وهميًا.

في الإنشاء الحالي يكون `status=UnderReview` و`restaurantApprovalStatus=Approved` و`adminApprovalStatus=Submitted`، ويذهب الإشعار إلى الإدارة مباشرة. إشعار التقديم قد يحمل `status=Submitted` رغم أن API الحالة يرجع `UnderReview`؛ المرجع للشاشة هو API الحالة.

### 4.3 حساب أنشأه المطعم

المطعم ينشئ الطلب والحساب دون أن يختار السائق كلمة مرور بنفسه. لا تعتبر ذلك اعتمادًا نهائيًا.

1. السائق يدخل الهاتف في شاشة الدخول.
2. استدعاء `lookup-phone`.
3. إذا `isFirstTimeSetup=true`، يكون السيرفر قد أرسل OTP في هذا المسار.
4. إدخال OTP وكلمة المرور الجديدة وإرسال `first-time-setup`.
5. حفظ الجلسة الصادرة، ثم تسجيل FCM وجلب الحالة.
6. يظل تشغيل التوصيل مقفولًا إلى استكمال الاعتماد والصلاحيات التشغيلية.

## 6. التسجيل الذاتي ورفع الملفات

### 6.1 رفع ملف

أرسل `multipart/form-data` بحقل **`file`**. حد الطلب في هذا endpoint هو `15 * 1024 * 1024` بايت للطلب بالكامل؛ اجعل حد الملف في التطبيق أقل قليلًا لتغطية multipart overhead.

الاستجابة تحتوي:

| الحقل | الاستخدام |
|---|---|
| `storageKey` | المفتاح الذي يوضع في حقول التسجيل وإعادة التقديم |
| `readUrl` | رابط عرض الملف؛ قد يكون نسبيًا، فحلّه مقابل عنوان API عند الحاجة |
| `fileName` | الاسم |
| `contentType` | النوع |
| `sizeBytes` | الحجم |
| `message` | رسالة نجاح مترجمة |

لا ترسل `readUrl` أو مسار الملف المحلي مكان `storageKey`. لا تملأ المفتاح قبل انتهاء رفع الملف بنجاح. فشل ملف واحد لا يُعرض كتسجيل ناجح.

التحقق الحالي يثبت وجود الملف وأنه غير فارغ، لكنه لا يثبت ملكية المفتاح للمستخدم؛ توجد فجوة بنية تحتية موضحة في القسم 13.

### 6.2 حقول طلب الإنشاء الكامل

| الحقل | القيد الحالي في التسجيل الذاتي |
|---|---|
| `restaurantId` | GUID أو null للمستقل |
| `fullNameAr`, `fullNameEn` | مطلوبان؛ طول كل منهما 3–200 |
| `phone` | مطلوب؛ حتى 30 حرفًا؛ يطابق `^\+?[0-9]{8,20}$` |
| `email` | اختياري؛ بريد صالح إن أُرسل، حتى 256 |
| `password` | مطلوب؛ 8 أحرف على الأقل، مع قبول سياسة Identity الفعلية |
| `nationalId` | مطلوب؛ 10–14 رقمًا |
| `nationalIdExpiry` | مطلوب؛ تاريخ بعد اليوم UTC |
| `dateOfBirth`, `nationality` | اختياريان |
| `vehicleType`, `vehicleModel` | مطلوبان |
| `vehiclePlate` | مطلوب؛ 2–30 حرفًا |
| `vehicleYear`, `vehicleColor`, `isVehicleOwned` | اختيارية؛ اللون حتى 50 حرفًا |
| `licenseNumber` | مطلوب؛ 5–50 حرفًا |
| `licenseExpiry`, `vehicleLicenseExpiry` | مطلوبان؛ تاريخ بعد اليوم UTC |
| `contractExpiry` | اختياري؛ إن أُرسل يجب أن يكون بعد اليوم UTC |
| `nationalIdFrontStorageKey`, `nationalIdBackStorageKey` | مطلوبان في هذا المسار |
| `drivingLicenseFrontStorageKey`, `drivingLicenseBackStorageKey` | مطلوبان في هذا المسار |
| `vehicleRegistrationStorageKey` | مطلوب |
| `profileImageStorageKey` | اختياري في validator الإنشاء، لكنه مطلوب للاعتماد النهائي؛ اجمعه في النموذج |
| `vehiclePhotoStorageKey` | اختياري |
| `contractStorageKey` | اختياري |

تواريخ الطلب بصيغة ISO 8601 مع timezone واضح. أمثلة أسماء الحقول في الطلب هي `vehicleLicenseExpiry` و`licenseExpiry`؛ تفاصيل التسجيل تستخدم أسماء مثل `vehicleRegistrationExpiryUtc` و`licenseExpiryUtc`. يلزم mapping صريح بين النموذجين.

السيرفر يتحقق من التكرار مثل الهاتف والبريد والهوية واللوحة؛ لا تكفي صحة الشكل في التطبيق لضمان قبول الإنشاء.

### 6.3 استجابة الإنشاء

استجابة نجاح `200` تحتوي `registrationId`, `restaurantId`, `restaurantName`, `fullName`, `fullNameAr`, `fullNameEn`, `phone`, `email`, `status`, `message` على مستوى DTO، مع تأثير الترجمة الموضح في القسم 12.

لا توجد جلسة دخول في هذه الاستجابة. خزّن المعرّف وربطه بالحساب، ثم نفّذ الدخول. خزّن كلمة المرور فقط حسب سياسة التطبيق الآمنة؛ لا تحفظها في تخزين عادي أو log.

### 6.4 المسار القديم ليس نفس العقد

يوجد أيضًا `POST /api/v1/auth/drivers/register`، وعقده مختلف: يستخدم مثلًا `drivingLicenseStorageKey` و`employmentContractStorageKey`، وينشئ مسار Draft ثم submit. لا تخلط حقوله مع عقد التسجيل الكامل أعلاه.

لو التطبيق مبني على المسار القديم، يجب مراجعته كمجموعة متكاملة: الإنشاء، التفاصيل، إرفاق المستندات، `PUT /api/v1/drivers/registrations/{id}` و`POST .../{id}/submit`. هذا المستند يستخدم التسجيل الذاتي الكامل كعقد الفلو ذي الثلاث خطوات. لم يُزل المسار القديم ولم تُوحّد كل سياساته مع المسار الكامل.

## 7. شاشة متابعة الطلب

### 7.1 عقد الاستجابة

| الحقل | المطلوب من الموبايل |
|---|---|
| `registrationId`, `phone`, `fullName` | التعريف والعرض |
| `fullNameAr`, `fullNameEn` | اختياريان من منظور parser بسبب اختيار اللغة |
| `restaurantId`, `restaurantName` | عرض جهة الطلب؛ المستقل قد يرجع GUID الصفري بدل null في status DTO |
| `status` | أساس القرار والتنقل |
| `stage` | نوع شاشة الحالة، وليس مرحلة مراجعة المطعم/الأدمن |
| `badge`, `title`, `subtitle`, `notice` | نصوص العرض؛ `notice` nullable |
| `rejectionReason` | سبب الرفض، nullable |
| `changeRequestNotes` | ملاحظات التصحيح، nullable |
| `restaurantApprovalStatus`, `adminApprovalStatus` | عرض خطوات المراجعة بشكل مستقل |
| `canResubmit`, `isApproved` | مساعدان للواجهة، مع استثناء الرفض الحالي |
| `requestedByRole` | `Admin` أو `Restaurant` عند التعديل/الرفض، وقد يكون null |

### 7.2 mapping الشاشات الحالي

| `status` | `stage` في API الحالة | الشاشة والسلوك |
|---|---:|---|
| `Submitted` أو `UnderReview` | 1 | قيد المراجعة؛ العمليات التشغيلية مقفولة |
| `NeedsChanges` | 2 | ملاحظات التعديل + نموذج التصحيح |
| `Rejected` | 3 | رفض + السبب؛ لا تتيح resubmit في العقد الحالي |
| `Approved` | 4 | نجاح الاعتماد؛ أعد تحميل بيانات الحساب والملف قبل فتح العمل |
| أي حالة أخرى | 1 حاليًا في mapper | تعامل محافظ وأعد الجلب؛ لا تفتح العمل من fallback |

عند `restaurantApprovalStatus=Approved` مع الطلب غير معتمد نهائيًا، توضح الواجهة أن المطعم وافق وأن الإدارة تراجع. لا تحول السائق إلى التشغيل من موافقة المطعم وحدها.

**تعارض الرفض الحالي:** `DriverStatusMapper` يرجع `canResubmit=true` عند `Rejected`، لكن resubmit يرجع `409 ALREADY_REJECTED`. قاعدة التطبيق المطلوبة حاليًا:

```text
showResubmit = canResubmit && status != Approved && status != Rejected
```

هذه معالجة توافق في التطبيق إلى أن يصلح الباك إند الحقل؛ لا تعرض للمستخدم عملية سيمنعها السيرفر.

### 7.3 التحديث وإعادة الدخول

- حدّث الحالة عند فتح الشاشة، والعودة للتطبيق، واستقبال/فتح إشعار تسجيل، وبعد نجاح إعادة التقديم.
- وفر سحبًا للتحديث ومحاولة جديدة عند فشل الشبكة.
- polling متباعد أثناء وجود المستخدم على شاشة المراجعة قرار تنفيذي مناسب؛ لا توجد مدة polling مفروضة في العقد.
- لا تعتبر الحالة المخزنة محليًا مصدرًا لفتح الصلاحيات.
- حالة `401` تحتاج استعادة الجلسة/الدخول ثم إعادة الطلب، و`403` ليست دليلًا على عدم وجود الطلب.

## 8. إعادة التقديم

`POST /api/v1/auth/staff/driver-registration/{registrationId}/resubmit` مع Bearer token لصاحب الطلب أو حساب أدمن مخول.

### 8.1 حقول body المدعومة

كلها اختيارية في عقد إعادة التقديم:

```text
licenseNumber, licenseExpiry,
vehiclePlate, vehicleModel, vehicleType, vehicleYear, vehicleColor,
isVehicleOwned, vehicleLicenseExpiry, contractExpiry,
nationalIdFrontStorageKey, nationalIdBackStorageKey,
drivingLicenseFrontStorageKey, drivingLicenseBackStorageKey,
vehicleRegistrationStorageKey, profileImageStorageKey,
vehiclePhotoStorageKey, contractStorageKey,
fullNameAr, fullNameEn, phone, email,
nationalId, nationalIdExpiry, nationality, dateOfBirth
```

أرسل الحقول المعدلة فقط. omission/null لا يعني حذف القيمة الحالية، والسلاسل الفارغة لا تعمل كعملية مسح للحقول. `isVehicleOwned=false` قيمة فعلية وليست حقلًا غائبًا.

مثال body لتغيير رقم الرخصة وتاريخها، دون تغيير الهاتف أو إعادة إرسال ملفات لم تتغير:

```json
{
  "licenseNumber": "NEW-LICENSE-123",
  "licenseExpiry": "2028-09-30T00:00:00Z"
}
```

المثال توضيحي للعقد، وليس بيانات اختبار أعمال جاهزة أو قيمة تعتمد في الإنتاج.

### 8.2 الحالات المسموحة والممنوعة

السيرفر يمنع `Approved` و`Rejected` أولًا. يسمح بـ`Draft` أو وجود `NeedsChanges` في الحالة الكلية أو إحدى المراجعتين. يرفض الطلب قيد المراجعة الذي لا يحمل حالة تسمح بالتعديل.

زر إعادة التقديم في تجربة المستخدم الأساسية يظهر عند طلب التعديل، وليس أثناء المراجعة أو بعد القرار النهائي. دعم Draft يخص المسار القديم وله احتياجات منفصلة.

بعد النجاح تُعاد استجابة الحالة. تصبح الحالة العامة `Submitted` ويُعاد ضبط مراجعة الأدمن إلى `Submitted` وتُمسح ملاحظات التصحيح/الرفض العامة. أعد رسم الشاشة من الاستجابة ثم جلب الحالة؛ لا تبقِ ملاحظات طلب التعديل القديم ظاهرة كأنها جديدة.

### 8.3 متى تعاد مراجعة المطعم؟

في المسار الحالي تُعد هذه تغييرات جوهرية:

- تغيير قيمة `nationalId` أو `licenseNumber` أو `vehiclePlate` بعد مقارنتها بالقيم السابقة.
- إرسال أي مفتاح جديد/غير فارغ للهوية أو الرخصة أو تسجيل المركبة أو الصورة الشخصية أو صورة المركبة أو العقد.
- إرسال `contractExpiry` بقيمة.

عند تغيير جوهري، لا تُحفظ موافقة المطعم السابقة؛ يعود الطلب المرتبط بمطعم إلى مراجعته. لذلك لا ترسل مفاتيح الملفات القديمة مع كل حفظ: إرسال المفتاح يُعامل كتقديم مستند حتى لو كان نفس المفتاح، وقد يعيد المراجعة.

إذا كان الأدمن طلب تعديلًا وكان المطعم وافق، ولم يحدث تغيير جوهري حسب القائمة السابقة، يمكن إبقاء موافقة المطعم والعودة للأدمن مباشرة. المسار المستقل يذهب للأدمن مباشرة.

لا تستنتج إعادة المراجعة في التطبيق بقائمة أوسع أو مختلفة؛ اعرض نتيجة السيرفر. مثلًا تغيير الاسم وحده ليس ضمن قائمة `fundamentalFieldsChanged` الحالية، رغم أنه تغيير مسموح في الطلب.

### 8.4 الهاتف

تغيير الهاتف يُرفض بـ`400` وكود `Driver.PhoneChangeRequiresVerification` قبل تغيير البيانات. إرسال الهاتف نفسه لا يعد تغييرًا.

ضع الهاتف للعرض فقط في نموذج التصحيح. لا تنفذ مسار OTP لتغيير الهاتف من عندك باستخدام verify-otp العام؛ endpoint إعادة التقديم لا يقبل دليل تحقق هاتف جديد في عقده الحالي.

## 9. دخول أول مرة وإعادة تعيين كلمة المرور

### 9.1 `lookup-phone`

Body: `{ "phone": "..." }`.

الاستجابة الحالية: `exists`, `isFirstTimeSetup`, `phone`, `fullName`, `restaurantName`, `status`.

- الحساب غير الموجود يرجع `404`؛ لا تفترض استجابة نجاح مع `exists=false`.
- عند أول إعداد تكون `isFirstTimeSetup=true`، ويرسل handler OTP بغرض `VerifyPhone`.
- `fullName` يرجع null حاليًا حتى للحساب الموجود.
- في أول إعداد تُحجب `restaurantName` و`status` وتعودان null.
- بعد إعداد كلمة المرور قد يرجع اسم المطعم والحالة، لكن `status` في هذا endpoint قد يكون حالة تسجيل أو حالة حساب fallback. لا تستخدمه بدل API الحالة.
- لا تضف استدعاء إرسال OTP تلقائيًا بعد كل lookup ناجح لأول إعداد؛ المسار أرسله بالفعل. إعادة الإرسال تكون بفعل المستخدم مع ضبط المحاولات.

### 9.2 `first-time-setup`

الحقول الدقيقة: `phone`, **`otpCode`**, **`password`**. OTP بطول 6، وكلمة المرور بطول 8 على الأقل مع سياسة Identity.

لا ترسل `otp` و`newPassword` و`confirmPassword` لهذا endpoint اعتمادًا على المستند القديم. تأكيد كلمة المرور يتم محليًا؛ ليس حقلًا في عقده الحالي.

النجاح يرجع DTO جلسة على المستوى الأعلى، وليس `{ user, tokens }`: من حقوله `userId`, `phoneNumber`, `userType`, `accountStatus`, `restaurantId`, `roles`, `permissions`, `accessToken`, `accessTokenExpiresAtUtc`, `refreshToken`, `refreshTokenExpiresAtUtc`, `nextStep`.

حفظ الجلسة ثم تحميل الحالة مطلوب حتى لو الحساب لم يعتمد بعد. لا تعرض الاسم/المطعم القديم الذي افترضته شاشة lookup قبل التحقق.

### 9.3 الدخول وكلمات المرور

- `/api/v1/auth/drivers/login`: أرسل `phone` و`password`؛ `email` اختياري كبديل. تجنب إرسال بريد قديم مع هاتف جديد لأن اختيار الحساب يعطي الأولوية للبريد في المسار الحالي.
- `/api/v1/auth/drivers/resend-otp`: `destination`, `channel`, `purpose`؛ لأول إعداد استخدم `channel="Phone"`, `purpose="VerifyPhone"`.
- `/api/v1/auth/drivers/verify-otp`: `destination`, `purpose`, `code`؛ لا ينتج من ذلك وحده إعداد كلمة المرور والجلسة المطلوبة.
- `/api/v1/auth/drivers/forgot-password`: `phone`.
- `/api/v1/auth/drivers/reset-password`: `phone`, `otpCode`, `newPassword`.

لا تستهلك رمز أول إعداد عبر verify-otp ثم تعيد استخدامه افتراضًا في first-time-setup؛ الأخير يتحقق من الرمز بنفسه. نفذ الإعداد عبر endpoint المخصص.

## 10. FCM ومركز إشعارات السائق

### 10.1 تسجيل الجهاز

يحتاج `POST /api/v1/driver/device-token` إلى Bearer token. التعليق القديم في controller عن التسجيل قبل الدخول لا يطابق `[Authorize]` ولا handler الحالي.

Body:

```json
{
  "token": "ACTUAL_FCM_TOKEN",
  "platform": "Android",
  "deviceId": "APP_DEVICE_IDENTIFIER",
  "registrationId": "ACTUAL_REGISTRATION_GUID"
}
```

القيم هنا وصفية؛ استبدلها بالقيم الفعلية. `platform` تكون `Android` أو `iOS`. `deviceId` و`registrationId` اختياريان. يمكن إرسال registrationId في query بدل body؛ قيمة query لها الأولوية إن أُرسلت.

للسائق العادي يُفضل الاعتماد على جلسة المستخدم وإرسال معرّف طلبه عند توفره؛ لا تمرر `driverId` قبل وجود ملفه التشغيلي.

- سجل token بعد الدخول، وبعد أول إعداد، وعند refresh الخاص بـFCM.
- يمكن التسجيل قبل الاعتماد النهائي طالما توجد جلسة.
- طلب إذن الإشعارات ورفضه لا يمنع تحميل الحالة ومركز الإشعارات.
- عند logout عطّل token قبل إبطال/مسح جلسة الدخول، ثم امسح ربطه المحلي.
- بديل التعطيل: `POST /api/v1/driver/device-token/deactivate` مع `{ "token": "..." }`.
- نجاح أوامر token وread يكون عادة `204` بلا body؛ لا تفشل parser بسبب غياب JSON.
- لا يمكن ضمان push لأول تسجيل إذا لم يدخل السائق ويسجل جهازه بعد؛ الحالة ومركز الإشعارات يعوضان ذلك عند الدخول.

### 10.2 أحداث التسجيل

| `eventKey` | المعنى | إجراء التطبيق |
|---|---|---|
| `driver.registration.submitted` | تم تقديم الطلب المرتبط بمطعم | تحديث الحالة، عرض انتظار المراجعة |
| `driver.registration.independent_submitted` | تقديم مستقل للإدارة | تحديث الحالة، عرض انتظار الإدارة |
| `driver.registration.resubmitted` | إعادة تقديم | تحديث الحالة وإزالة واجهة الملاحظات القديمة وفق الاستجابة |
| `driver.registration.restaurant_approved` | المطعم وافق | تحديث الحالة؛ استمرار انتظار الاعتماد النهائي |
| `driver.registration.restaurant_changes_requested` | المطعم طلب تعديلًا | فتح الحالة ثم التصحيح |
| `driver.registration.restaurant_rejected` | رفض المطعم | عرض سبب الرفض من الحالة |
| `driver.registration.admin_approved` | اعتماد المنصة | تحديث الحالة والملف والبيانات التشغيلية |
| `driver.registration.admin_changes_requested` | الإدارة طلبت تعديلًا | فتح الحالة ثم التصحيح |
| `driver.registration.admin_rejected` | رفض الإدارة | عرض سبب الرفض من الحالة |

Payload البيانات يستخدم قيم string؛ من الحقول `registrationId`, `stage`, `status`, `restaurantName`، ومع بعض الأحداث `restaurantId`, `reviewStage`, `notes`, `reason`. لا تعتبر جميعها إلزامية في كل حدث.

**فرق stage:**

- API الحالة: 1 مراجعة، 2 تعديل، 3 رفض، 4 قبول.
- إشعار التقديم/إعادة التقديم: `stage` و`reviewStage` يشيران إلى 1 مراجعة مطعم أو 2 مراجعة إدارة.
- إشعار موافقة المطعم يحمل `stage="2"` رغم أن الشاشة تظل «قيد المراجعة» وليست شاشة تعديل.

لذلك لا تستخدم رقم stage من FCM مباشرة لاختيار شاشة الحالة. اقرأ `eventKey` للتوجيه ثم اجلب الحالة.

### 10.3 فتح الإشعار

الإشعار المحفوظ يستخدم deep link بالشكل `/driver/status?registrationId=...`. حوّله إلى route داخلي في التطبيق؛ ليس رابط API ولا تصريحًا لعرض طلب أي شخص.

إذا التطبيق مغلق أو المستخدم خارج الجلسة، احفظ وجهة التنقل مؤقتًا، نفذ الدخول، ثم اجلب الحالة الخاصة بالطلب. عالج `403` لو الحساب الحالي لا يملك الطلب. الأحداث القديمة والمتأخرة لا ينبغي أن تعيد الشاشة إلى حالة سابقة بعد الاعتماد.

push وسيلة إعلام غير متزامنة. لا تعتمد على وصوله مرة واحدة أو وصوله بالترتيب. لا تتجاهل كل حدث يحمل نفس `eventKey + registrationId` للأبد، لأن هناك دورات إعادة تقديم حقيقية متعددة.

### 10.4 القائمة والمقروء

`GET /api/v1/driver/notifications` يرجع **array مباشرة** من آخر 50 إشعارًا، مرتبة من الأحدث. لا توجد pagination أو `unreadOnly` أو `unreadCount` في عقد السائق الحالي.

حقول العنصر: `notificationId`, `type`, `title`, `body`, `sentTimeAgo`, `isRead`, `section`, `subjectId`, `deepLink`, `sentAtUtc`.

تحميل القائمة يعمل بإشعارات `UserId` قبل الاعتماد وبملف السائق بعده. لا تشترط وجود driver profile لفتحها. إشعارات التسجيل المحفوظة تستخدم `section="registration"`.

عد غير المقروء محليًا داخل العناصر المحملة فقط؛ ليس إجماليًا مضمونًا لكل تاريخ الحساب. لا تعرض «تحميل المزيد» اعتمادًا على APIs الأدمن أو المطعم لأنها مختلفة.

لتعليم إشعار: `PUT /api/v1/driver/notifications/{notificationId}/read`، بدون body مطلوب. لا تعلمه مقروءًا نهائيًا في الواجهة إذا فشل الطلب دون إمكانية تصحيح/إعادة محاولة.

## 11. الاعتماد، الجاهزية والمستندات

### 11.1 الاعتماد لا يساوي online

لا تفتح التشغيل لمجرد JWT صالح أو موافقة المطعم أو وصول push موافقة. أعد تحميل الحالة والملف وبيانات الحساب المتاحة، واحترم أخطاء الـAPIs التشغيلية.

حالة الحساب الموقوف/المغلق أو بيانات الجاهزية المفقودة يجب ألا تعرض «جاهز للعمل». لا تجعل missing/null تتحول تلقائيًا إلى Active/Available.

endpoint الملف الفعلي هو **`GET /api/v1/driver/profile`**، وليس `/api/v1/drivers/me/profile` الوارد في دليل قديم. استجابته تشمل `driverProfileId`, `fullName`, `phoneNumber`, `isOnline`, `status`, `statusText`, `vehicle`, `documents`, `assignment` ومؤشرات تشغيلية. هذا العقد لا يقدم `accountStatus` كحقل مستقل؛ لا تخترع حقلًا في parser.

غياب ملف تشغيلي قبل الاعتماد يُعرض كشاشة متابعة التسجيل، ولا يتم استبداله بملف وهمي. بعد الاعتماد أعد جلب الملف وحالة الجلسة عبر مسارات التطبيق القائمة، ولا تعدّل `accountStatus` في cache اعتمادًا على push فقط.

### 11.2 المستندات

في الاعتماد النهائي الحالي تُراجع الصورة الشخصية، الهوية، رخصة القيادة وتسجيل المركبة وتواريخها، وأي عقد موجود. الملفات المطلوبة يجب أن تكون موجودة وغير فارغة، وآخر نسخ المستندات المرفوضة/المنتهية تمنع الاعتماد.

الهوية/الرخصة الأمامية أو النوع المدمج مطلوبان في قرار الاعتماد؛ الخلفية إذا موجودة تُفحص أيضًا. التسجيل الذاتي الكامل نفسه يطلب الخلفيتين. هذه سياسات مختلفة بين مراحل ومسارات النظام، فلا تجعل الخلفيات اختيارية في نموذج التسجيل الكامل اعتمادًا على قرار الاعتماد وحده.

عقد العمل وصورة المركبة اختياريان في نموذج الإنشاء الحالي. الصورة الشخصية اختيارية في validator الإنشاء لكنها لازمة للاعتماد النهائي؛ هذا فرق فعلي في النظام.

شاشة الملف ترجع للمستندات `documentId`, `documentType`, `documentTitle`, `status`, `statusText`, `verificationStatus`, `expiryDate`, `daysUntilExpiry`, `requiresRenewal`. راعِ أن وثيقة منتهية لا تعرض كمستند صالح فقط لأن verification قديم Approved. استخدم تاريخ الانتهاء والحالة/علامة التجديد، وحدّثها بعد التجديد.

## 12. الترجمة والأخطاء والتوافق

### 12.1 اللغة

أرسل `Accept-Language: ar` أو `en` باستمرار؛ النظام يدعم أيضًا `Language` و`X-Language`.

الاستجابات المترجمة قد تحتوي على الاسم العام مثل `fullName` مع الحقل الخاص باللغة المطلوبة (`fullNameAr` أو `fullNameEn`) وتحذف اللغة الأخرى. لا تجعل وجود الحقلين شرطًا لنجاح parsing.

في نموذج تصحيح يحتاج فعلًا إلى اللغتين يمكن طلب `X-Bilingual: true` لجلب حقول المصدر. تجنب فقدان اللغة غير المعروضة أو إرسال نص مترجم مكان الأصل. تغيير اللغة يقتضي تحديث بيانات العرض من API.

لا تستخدم النصوص `badge/title/subtitle` أو رسائل الخطأ لتحديد الحالة؛ استخدم status/code. لا تُفترض لغة FCM مساوية تلقائيًا للغة طلب API؛ راجع payload الفعلي في بيئة الأجهزة.

### 12.2 الأخطاء

الـAPI يحول فشل النتيجة إلى ProblemDetails يحتوي مثلًا `status`, `title`, `detail`, `instance`, `code`. لا تتوقع wrapper باسم `success/data` في APIs المعروضة هنا.

| HTTP / code | تعامل التطبيق |
|---|---|
| 400 / `Driver.PhoneChangeRequiresVerification` | تثبيت الهاتف وإيضاح أن تغييره غير مدعوم في هذه العملية |
| 400 / `Resubmit.EmptyChanges` | طلب تعديل حقل أو رفع مستند قبل إعادة التقديم |
| 400 / `Driver.InvalidStoredDocument` | إظهار الملفات غير المتاحة/الفارغة وإتاحة الرفع مجددًا |
| 409 / `ALREADY_APPROVED` | إعادة تحميل الحالة، إغلاق التصحيح |
| 409 / `ALREADY_REJECTED` | إعادة تحميل حالة الرفض، إغلاق التصحيح |
| 409 / `INVALID_TRANSITION` | إعادة تحميل الحالة؛ ربما تغيرت عند المراجع |
| 409 / تعارض هاتف/هوية/لوحة/بريد | عرض detail على الحقل المناسب؛ لا تكرر الإنشاء تلقائيًا |
| 401 | تجديد/استعادة جلسة حسب مسار التطبيق ثم إعادة العملية بأمان |
| 403 | عرض عدم الصلاحية/حالة الحساب؛ لا تعتبر تغيير المعرّف حلًا |
| 404 | الطلب/الحساب غير موجود؛ وفر رجوعًا أو محاولة مناسبة |
| 413 | حجم الرفع تجاوز حد الطلب |
| 429 | احترام الانتظار/Retry-After إن وُجد وإيقاف إعادة المحاولات السريعة |
| 422 أو 5xx | رسالة فشل وإعادة محاولة واعية؛ لا تعرض موافقة أو نجاحًا افتراضيًا |

إرسال التسجيل ليس مضمونًا idempotent من جهة الموبايل. بعد timeout قد يكون السيرفر حفظه؛ لا تنشئ طلبًا ثانيًا تلقائيًا. استخدم الدخول/الاستعلام عن الحالة الخاصة بالحساب لتحديد النتيجة، وعالج conflict بدل تدوير محاولات إنشاء جديدة.

## 13. الفجوات المعروفة التي لم تُغلق بالكامل

| الفجوة | الحالة الفعلية | أثرها والتنسيق المطلوب |
|---|---|---|
| تغيير الهاتف مع تحقق جديد | لا يوجد عقد purpose-bound مخصص؛ التغيير مرفوض | لا تنفذه في التصحيح؛ يحتاج backend API مستقل قبل فتحه |
| ملكية الملفات المرفوعة | وجود/محتوى الملف مفحوصان، ولا توجد metadata محفوظة تثبت مالك upload | لا تدّعِ أن السيرفر تحقق من ملكية المفتاح؛ تحتاج بنية upload ownership |
| idempotency نهائية لكل تسليم إشعار | يوجد InboxProcessedEvents بمعرّف Outbox على مستوى consumer، لكن حفظ الإشعار/الإرسال لا يستخدم eventId دائمًا؛ توجد نافذة dedup زمنية قصيرة | يمكن حدوث duplicate أو فقد تمييز دورات متقاربة؛ التطبيق يجلب الحالة ولا يعد push حدثًا فريدًا مضمونًا |
| retry كامل لكل المستلمين | مسار إرسال/حفظ إشعار السائق يسمح بانتشار الفشل، لكن بعض أخطاء إشعارات الأدمن/المطعم ما زالت تلتقط وتُسجل | لا يقال إن كل قنوات الإشعار مضمونة؛ يحتاج اختبار وإصلاح إضافي |
| `canResubmit` عند الرفض | true في mapper، مع منع command للعملية | تطبيق guard حالة الرفض الموضح أعلاه، مع طلب تصحيح backend للحقل |
| stage في API وFCM | معنيان مختلفان بحسب السياق | عدم استخدام FCM stage مباشرة لاختيار شاشة |
| أول تسجيل ذاتي والتحقق من الهاتف | إنشاء anonymous مع كلمة مرور؛ لا يتطلب عقده OTP مكتملًا | لا توصف رحلة الإنشاء بأنها تحقق ملكية هاتف كامل من السيرفر |
| خصوصية lookup | بيانات أول إعداد محجوبة، لكن قد تظهر حالة/مطعم لحساب سبق ضبطه قبل الدخول | لا توسع عرض البيانات؛ يحتاج تدقيق privacy إضافي |
| قائمة إشعارات السائق | آخر 50 فقط؛ لا يوجد عداد إجمالي أو paging | عدم الادعاء بتحميل كامل التاريخ أو إجمالي غير المقروء |
| عدة عقود تسجيل | legacy وstaff الكامل ليسا متطابقين | تحديد المسار الذي يستخدمه التطبيق وعدم خلط DTOs أو شروط المستندات |
| جاهزية التشغيل في تطبيق الموبايل | لا يوجد في status DTO حقل جامع لكل حالة الحساب والتوفر | استخدام بيانات التطبيق التشغيلية القائمة واحترام قرار السيرفر؛ لا اختراع ready=true |

هذه الفجوات لا تُحل بتغيير أسماء حقول في الموبايل. أي اعتماد للإصدار يجب أن يميز ما تم تنفيذه بالفعل مما يحتاج backend work.

## 14. ما تغير في لوحتي المطعم والأدمن

هذا القسم يوضح ما قد يراه السائق نتيجة قرارات المراجعين، ولا يتطلب استدعاء APIs الأدمن من تطبيقه.

- **المطعم:** إعادة تقديم تغييرات جوهرية تعيده لمراجعة الطلب، إنشاء السائق لا يتجاوز اعتماد المنصة، الوثيقة المنتهية تظهر منتهية، والجاهزية مبنية على حالة الحساب والتوفر بدل موافقة الطلب وحدها.
- **قائمة طلبات المطعم:** تحميل كل صفحات التسجيل بدل الاقتصار على أول 100، مع الاحتفاظ بالنتائج الجزئية وإعادة المحاولة عند فشل صفحة.
- **إشعارات المطعم:** endpoint paged إضافي مع فلتر غير المقروء وعداده، مع الحفاظ على endpoint القديم. لا يُطبق عقده على مركز إشعارات السائق.
- **الأدمن:** عرض تاريخ مراجعة الطلب مع الفاعل والإجراء والسبب والتاريخ والتصفح؛ إشعارات الأدمن تستخدم paging/فلتر/عداد من السيرفر.
- **قرارات الاعتماد:** تحقق من المالك الحقيقي للطلب، المستندات وآخر النسخ والتواريخ قبل إنشاء/تفعيل نتائج الاعتماد؛ الإشعارات تُرسل عبر أحداث المراجعة.
- **تاريخ مراجعات الأدمن:** `GET /api/v1/admin/drivers/registrations/{id}/history` محمي بصلاحية `DriverRegView`. ليس endpoint تاريخ متاحًا تلقائيًا لكل سائق، فلا تبنِ عليه شاشة موبايل للسائق دون عقد وصلاحية مخصصة.

## 15. ترتيب تنفيذ الموبايل

- [ ] **Models:** فصل RegistrationStatus وAccountStatus وProfileStatus؛ حفظ المعرّفات المختلفة؛ parsing للحقول nullable واللغة الواحدة.
- [ ] **Registration API:** تثبيت مسار التسجيل الكامل أو توثيق بقاء التطبيق على legacy؛ تنفيذ catalogs ورفع الملفات والـmapping الصحيح للتواريخ والمفاتيح.
- [ ] **Authentication:** استجابة التسجيل بدون tokens؛ login مستقل؛ lookup/first-time-setup بالحقول الصحيحة؛ حفظ الجلسة الآمن.
- [ ] **Application status:** الشاشة تستند إلى status API؛ فصل المراجعتين؛ منع resubmit للرفض/الاعتماد رغم canResubmit الحالي.
- [ ] **Resubmit form:** الحقول المعدلة فقط؛ هاتف غير قابل للتعديل؛ عدم إرسال ملفات لم تتغير؛ ملاحظات المراجع واضحة.
- [ ] **FCM:** تسجيل token بعد الدخول وقبل الاعتماد؛ refresh/logout؛ foreground/background/cold start؛ pending navigation بعد الدخول.
- [ ] **Inbox:** array آخر 50، read endpoint، عداد للعناصر المحملة، وإعادة جلب الحالة عند فتح إشعار تسجيل.
- [ ] **Operational access:** لا تشغيل من موافقة المطعم أو push؛ تحميل الملف الحقيقي واحترام حالة الحساب/قرارات APIs التشغيلية.
- [ ] **Localization/errors:** اللغة، X-Bilingual عند الحاجة لتحرير اللغتين، ProblemDetails، 204، retry وtimeouts دون إنشاء مكرر.
- [ ] **Acceptance:** تنفيذ الجدول التالي وإرفاق نتائج البيئة والأجهزة مع تسليم الموبايل.

## 16. سيناريوهات الاختبار والقبول

| السيناريو | النتيجة المطلوبة |
|---|---|
| تسجيل مرتبط بمطعم | حفظ registrationId، دخول مستقل، عرض انتظار المطعم |
| تسجيل مستقل | لا يُطلب اختيار مطعم؛ عرض انتظار الإدارة حتى لو restaurantApprovalStatus=Approved |
| upload فاشل/فارغ/أكبر من الحد | لا نجاح وهمي؛ إعادة رفع واضحة |
| storageKey غير موجود | عرض خطأ مستند، عدم الانتقال لنجاح التسجيل |
| تاريخ مستند اليوم أو في الماضي | منع/عرض رفض التحقق؛ التاريخ يجب أن يكون لاحقًا |
| هاتف أو هوية أو لوحة مستخدمة | عرض conflict مفهوم دون تكرار الإنشاء |
| تسجيل timeout بعد الإرسال | فحص النتيجة بالحساب/الحالة؛ عدم إنشاء طلب ثانٍ تلقائيًا |
| login لحساب Registered تحت المراجعة | شاشة متابعة؛ لا تشغيل توصيل |
| حساب أنشأه المطعم | lookup يرسل OTP، ثم first-time-setup بالحقول الدقيقة ويصدر جلسة |
| lookup لا يعيد الاسم/المطعم | نموذج لا ينهار ولا يعرض قيمة مخترعة |
| OTP خاطئ/منتهي | عرض الفشل وإعادة الإرسال المناسبة دون استهلاك الرمز في عمليتين |
| status/resubmit/device-token بلا token | معالجة 401، وعدم اعتبار المعرّف كافيًا |
| طلب لسائق آخر | معالجة 403 وعدم عرض بياناته |
| FCM قبل وجود DriverProfile | التسجيل بعد الدخول ينجح، والقائمة تعمل عبر UserId |
| موافقة المطعم | استمرار شاشة المراجعة؛ لا تشغيل؛ FCM stage=2 لا يفتح نموذج تعديل |
| طلب تعديل من المطعم | عرض requestedByRole والملاحظات، ثم إعادة التقديم |
| طلب تعديل من الأدمن دون تغيير جوهري | قراءة النتيجة من السيرفر؛ يمكن بقاء موافقة المطعم |
| تغيير هوية/رخصة/لوحة أو رفع ملف جديد | إعادة مراجعة المطعم في الطلب المرتبط به |
| حفظ النموذج دون تغيير | منع الزر أو عرض Resubmit.EmptyChanges |
| تغيير الهاتف | الحقل مقفول؛ إن وصل API يعرض PhoneChangeRequiresVerification |
| إرسال الحقول التي لم تتغير | لا ترفع ملفات/ترسل مفاتيح قديمة بلا داعٍ؛ لا إعادة مراجعة غير مقصودة |
| رفض الطلب | إظهار السبب؛ زر resubmit مخفي رغم true الحالية |
| اعتماد أثناء فتح نموذج تعديل | 409 ثم إعادة جلب الحالة وإغلاق النموذج |
| approval push قديم بعد حدث أحدث | الحالة الفعلية تحدد الشاشة، لا ترتيب وصول push |
| رفض إذن notifications | الفلو يكمل عبر status/inbox |
| FCM token refresh/logout | تحديث token وتعطيله قبل إزالة الجلسة |
| التطبيق مغلق ثم ضغط إشعار | login عند الحاجة ثم فتح حالة الطلب الصحيح |
| إشعار مكرر | لا تكرار تنقل مربك؛ لا تجاهل دورات resubmit اللاحقة للأبد |
| تحويل ar إلى en | لا crash بسبب حذف fullNameAr/fullNameEn؛ عرض النص المناسب |
| نجاح 204 للقراءة/token | لا توقع JSON إجباري |
| قائمة بها 50 إشعارًا | لا ادعاء وجود pagination أو إجمالي كامل |
| مستند Approved لكنه انتهى | عرض انتهاء/تجديد، لا «صالح» من approval وحدها |
| موافق عليه لكن الحساب موقوف أو بيانات التشغيل مفقودة | لا فتح عمل افتراضي؛ احترام رد السيرفر |

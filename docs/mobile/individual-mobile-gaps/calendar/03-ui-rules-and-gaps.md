# 6 — قواعد الواجهة ونواقص شائعة في التقويم

> عقد الشاشات المرجعي: [`../../individual-calendar/00-individual-calendar-flow.md`](../../individual-calendar/00-individual-calendar-flow.md)

## قواعد مقفولة لازم تطابق الـAPI

1. يوم واحد = مطعم واحد = بوكس واحد.
2. عدد الوجبات = خانات الباقة (`slotRequirements`) بالضبط قبل تفعيل «تم».
3. التعديل فقط قبل مهلة −72 ساعة؛ بعدها قراءة فقط.
4. الحساسية Hard Block — لا تجاوز `blockReason`.
5. مطاعم التقويم من pool الاشتراك فقط — ليست شبكة تصفح التصنيف قبل الدفع.

## نواقص متكررة في تطبيقات الموبايل

| ناقص | الأثر | الإصلاح |
|------|--------|---------|
| فتح التقويم قبل `calendar` 200 | شاشة فاضية/أخطاء | بوابة الدفع→التفعيل |
| استخدام مطاعم checkout/tier داخل التقويم | مطاعم غير مضمونة للاشتراك | `GET .../subscriptions/{id}/restaurants` |
| حفظ وجبة واحدة أو خانة ناقصة | رفض من الباك | أرسل كل `mealIds` دفعة |
| تجاهل `blockReason` | اختيار غير صالح | عطّل العنصر |
| عدم إعادة جلب التقويم بعد الحفظ | UI قديم | `GET /calendar` بعد كل حفظ |
| زر «تم» منفصل عن مسار غير موجود على الحي | 404 | الحفظ عبر `POST .../meals` |
| عدم احترام حد تكرار المطعم في UI | المستخدم يختار فوق الحد ثم يُرفض | اعرض الحد واحسب مرات الاستخدام من أيام التقويم |

## حد تكرار المطعم (عرض)

- الحد يُحسب من **عدد مطاعم الـpool × مدة الاشتراك** (منطق الباك؛ حد أدنى تشغيلي 3).
- في التقويم: احسب كم يومًا اختير فيه نفس `restaurantId` ضمن أيام الاشتراك، وامنع تجاوز الحد بينما بدائل متاحة.
- لا تثبت رقمًا في الكود؛ إن وصل حقل صريح من الملخص/الاشتراك لاحقًا استخدمه، وإلا احسب من بيانات الأيام + حجم pool.

## حالات Loading / Empty / Error

كل شاشة تقويم تحتاج:

- Loading أثناء جلب calendar / restaurants / meals
- Empty: لا اشتراك نشط → CTA للاشتراك
- Error + Retry على فشل الشبكة أو 5xx
- Offline واضح

## Checklist مبرمج التقويم

- [ ] بوابة بعد الدفع تعمل (payment → calendar)
- [ ] عرض الشهر/الأيام من `serviceDate` فقط
- [ ] اختيار مطعم من pool المجمّد
- [ ] تجميع الوجبات حسب `slot`
- [ ] تعطيل المحظور بالحساسية
- [ ] حفظ كامل + تحديث الحالة
- [ ] قفل الأيام بعد المهلة
- [ ] لا تعتمد مسارات غير مرفوعة

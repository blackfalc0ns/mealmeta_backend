# تاريخ البداية الافتراضي في فلو العائلة

عند إنشاء العائلة أو إضافة فرد أو قراءة `current` أو `summary`، يملأ الباك تاريخ البداية المفقود للفرد غير المشترك ويحفظه في PostgreSQL. التاريخ الافتراضي هو اليوم حسب توقيت الكويت، وليس قيمة ثابتة داخل الكود. الاختيارات المحفوظة لا تتغير عند إعادة القراءة، ولا تتغير بيانات الأفراد المدفوعين أو دفعات الدفع المعلقة.

## الحقول

- `members[].startDate`: يوم البداية المختار المحفوظ. يملؤه الباك افتراضيًا إذا كان ناقصًا.
- `memberSchedules[].firstDeliveryDate`: أول يوم تسليم محسوب من اليوم المختار، بعد تطبيق فترة التحضير والجمعة طبقًا لخدمة الجدولة المشتركة.
- `memberSchedules[].endDate`: آخر يوم تسليم حسب المدة وإعداد الجمعة.

لا تعرض `startDate` بوصفه أول يوم تسليم، ولا ترسل `firstDeliveryDate` بدلًا منه؛ ذلك سيطبق فترة التحضير مرتين. مثال فعلي بتاريخ 2026-10-13 بدون الجمعة: `startDate=2026-10-13` و`firstDeliveryDate=2026-10-17`.

## تغيير الاختيار

```http
PUT /api/v1/customer/family-subscription-flow/members/{memberId}/start-date
Content-Type: application/json
```

```json
{
  "startDate": "2026-10-23"
}
```

هذا مثال تاريخ لتوضيح العقد؛ يرسل الموبايل التاريخ الذي اختاره المستخدم فعليًا. بعد نجاح الطلب، استخدم الشاشة المعادة ثم أعد جلب الملخص بالفرد الصحيح:

```http
GET /api/v1/customer/family-subscription-flow/summary?memberId={memberId}
```

اقرأ `restaurants` و`availability` من الرد الجديد. تغيير تاريخ البداية قد يغير المطاعم المؤهلة لفترة الاشتراك. لا تتجاهل التغيير بسبب كاش قديم، ولا تستبدل تاريخ المستخدم بالافتراضي أثناء إعادة بناء الشاشة.

## الشراء

عند وجود فرد مختار للشراء غير متاح للفترة، يرجع الملخص `canCheckout=false` و`checkoutBlockReason` من سبب عدم التوفر. قد تكون مطاعم الفرد المعروض متاحة لكن الشراء محجوب بسبب فرد آخر مختار في نفس الدفعة؛ اعرض أسباب `memberSchedules` للأفراد المختارين.

لا يعني التاريخ الافتراضي أن الوجبات مناسبة لكل حساسية أو أن جميع الباقات جاهزة. تظل شروط تغطية العنوان والوجبات والجدول والسعر والتصنيف والطاقة الاستيعابية مطبقة.

## التحقق

تم تشغيل 80 اختبارًا لمسارات فلو العائلة بنجاح، تشمل حفظ التاريخ الافتراضي وإعادة قراءته، الفرد الجديد، بقاء اختيار المستخدم، معالجة الأفراد القدامى ذوي التاريخ المفقود، عدم تغيير الأفراد المدفوعين أو الدفع المعلق، وحجب الشراء عند عدم توفر المطاعم.
